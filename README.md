# pdftools

跨平台桌面 PDF 工具箱。单文件绿色程序，**不联网、不上传、文件不出本机**。

用 Rust + egui 写成，Windows / macOS / Linux 三平台都有预编译包。

## 功能

| 功能 | 说明 |
| --- | --- |
| **多图片转 PDF** | 拖进来、拖动排序、一键合成。页面尺寸与比例逐张跟随图片，没有白边。**默认无损，一个像素都不动**。拍摄时间从 EXIF/XMP/IPTC 读出并写进 PDF，读不到时可手动填 |
| **Word 转 PDF** | 纯 Rust 自研排版，不需要装 Word 或 LibreOffice。保真度有明确边界，见下文 |
| **PDF 压缩** | 四个档位。针对 PDF 内的图像重新编码，带多重护栏，绝不会越压越大，且保留原文件的创建时间 |
| **图片批量压缩** | 输出到指定目录，不改动原文件 |

## 下载

**<https://github.com/zzhtl/pdftools/releases/latest>**

下载即用，不需要解压，也不需要安装运行时。

| 平台 | 文件 | 怎么用 |
| --- | --- | --- |
| Windows (x64) | `pdftools-windows-x86_64.exe` | 下载后直接双击 |
| macOS (M 系列芯片) | `pdftools-macos-apple-silicon.dmg` | 双击挂载，把图标拖进 Applications |
| Ubuntu / Debian (x64) | `pdftools_<版本>_amd64.deb` | `sudo apt install ./pdftools_<版本>_amd64.deb` |

每个文件旁边都有 `.sha256` 校验文件。

### Linux 安装说明

用 `apt install ./xxx.deb` 而不是 `dpkg -i`——前者会自动把依赖装上，后者不会。装完之后：

- 在应用菜单里能直接找到 pdftools
- 命令行输 `pdftools` 也能启动，`pdftools 照片1.jpg 照片2.jpg` 可以直接带文件打开
- 卸载：`sudo apt remove pdftools`

这个包在 **Ubuntu 22.04** 上构建，因此 22.04 及更新的版本都能装（反过来不行——在新系统上构建的包会要求更高版本的 glibc）。

非 Debian 系的发行版（Fedora、Arch 等）没有预编译包，从源码构建即可，见文末。

macOS 只提供 M 系列（Apple Silicon）的包。Intel Mac 没有预编译版本，需要的话同样从源码构建。

### macOS 首次打开会被拦截

本项目**没有 Apple 开发者签名**，所以 macOS 会提示「无法打开，因为无法验证开发者」。这不是程序有问题，处理方式二选一：

- 在「应用程序」里**右键点击** pdftools → **打开**，在弹窗里再点一次「打开」；或者
- 终端执行：`xattr -dr com.apple.quarantine /Applications/pdftools.app`

### Windows SmartScreen

同理，未签名程序首次运行会被 SmartScreen 拦。点「更多信息」→「仍要运行」。

## 关于「不失真」

图片转 PDF **默认是无损档**，这一档的承诺是硬的：**绝不改动任何一个像素**。

- **JPEG**：原始字节整段搬进 PDF，不解码也不重新编码。有一条集成测试直接断言「PDF 里的流字节 == 源文件字节」。
- **横拍的手机照片**同样直通。EXIF 方向不是靠旋转像素来纠正的，而是写进 PDF 的变换矩阵 —— 照片摆正了，字节一个没动。八种 EXIF 方向都有测试逐一比对过渲染结果。
- **PNG 等无损格式**：逐像素无损存储。
- **不降采样、不缩放**，多大的图都原样进去。

如果确实需要把体积压下来，可以手动切到另外三档（高质量 / 平衡 / 极致）。它们会对超过 DPI 上限的图重新采样，界面上会用醒目的颜色提示「该档位不再是逐像素无损」。这几档里有两条护栏：

- 用 JPEG 还是无损存储，**不靠猜图片是不是照片，而是两种编码各估一次体积后按实测结果决定**。截图和线稿会自然选到无损，从而避开 JPEG 在文字边缘产生的振铃（那正是俗称的「发虚」）；照片会自然选到 JPEG。
- 如果降采样加重新编码之后**反而比原文件更大**，就退回原图直通 —— 那种情况既不省空间又白白损失一代画质。

## 时间信息

对取证类材料，「这张照片是什么时候拍的」往往比照片本身还关键。

### 拍摄时间从哪来

程序按可信度依次读三个**嵌在文件内部**的来源：

1. **EXIF** `DateTimeOriginal` —— 相机按下快门的时刻，最可信
2. **XMP** `xmp:CreateDate` / `photoshop:DateCreated` —— EXIF 被剥掉后这里常常还留着
3. **IPTC** `DateCreated` + `TimeCreated`

这三个都随文件本身走，**重命名、复制、转发都不会改变**。

### 文件时间不会被当成拍摄时间

三个来源都读不到时，列表里会显示文件系统时间，但明确标成「文件时间·非拍摄时间」，**并且不会写进 PDF**。

原因很直接：文件时间不可靠。重命名虽然不改 `mtime`，但**任何一次复制都会把它刷成当前时刻** —— 从手机导到电脑、微信接收、网盘同步，全都是复制。把它填进 PDF 的「创建时间」，等于在材料里凭空造一个拍摄日期。

所以：**有真实拍摄时间**时，PDF 的 `/CreationDate` 记最早那张的拍摄时刻；**一张都没有**时，`/CreationDate` 退回 PDF 规范的本义（本次导出时刻），并在「主题」字段里写明「原始文件中没有拍摄时间信息」。界面也会提示。

### 拍摄时间丢了怎么办

拍摄时间丢失比想象中常见：经微信、部分网盘、以及任何「清除元数据」操作转发过的照片，`DateTimeOriginal` 通常已被剥掉（典型特征是 `OffsetTimeOriginal`、`SubsecTimeOriginal` 这些配套标签还在，唯独日期没了）。

两个办法：

- **用手机相册里的原图**导出，不要用聊天软件里收到的那一份 —— 这是唯一能拿回真实拍摄时间的途径；
- 或者在列表里**直接填写**。每一行的时间都可以编辑，接受 `2024-03-15 14:30`、`2024/03/15 14:30:22` 等写法。同一场拍摄的照片可以用「把第一张的时间套用到全部」一次填完。

  **手动填写只影响生成的 PDF，不会修改图片文件本身。** 图片的 EXIF 仍然没有拍摄时间，下次在别的软件里打开还是读不到。本程序**不提供**把时间写回图片 EXIF 的功能：往一张从来没有拍摄时间的照片里写入 `DateTimeOriginal`，得到的元数据与相机原生写入无法区分，对需要举证的材料来说，「照片没有时间 + 另行说明」比一份看不出被改过的元数据更经得起推敲。

### 其他

- 列表可**按拍摄时间排序**。
- `/ModDate` 始终是导出时刻。
- Word 转 PDF 时，`/CreationDate` 沿用 docx 自己的创建时间。
- PDF 压缩会**保留原文件的创建时间**，只更新修改时间。
- 命令行或「用 pdftools 打开」传入的文件会按类型自动进到对应的功能页。

## Word 转 PDF 的支持范围

这一项是**纯 Rust 自己实现的排版引擎**，不调用任何外部程序。好处是绿色单文件、离线可用；代价是保真度有边界。请务必先看清楚：

**支持**

- 段落、粗体 / 斜体 / 下划线 / 删除线、字号、字体颜色
- 对齐（左 / 居中 / 右 / 两端对齐）
- 缩进（含「首行缩进 2 字符」这类以字符为单位的写法）
- 段前段后间距、行距（倍数 / 固定值 / 最小值）
- **行网格**（`w:docGrid`）—— 中文文档排版的关键，见下文
- **中西文自动间距**（`w:autoSpaceDE` / `w:autoSpaceDN`），「第 9 条」里的那点空隙
- 页面尺寸与页边距、显式分页符
- 中西文混排：ASCII 字符走西文字体，汉字与中文标点走中文字体，与 Word 的 `w:rFonts` 规则一致
- 符合 UAX #14 的断行，含中文标点避头尾（句号、逗号不会跑到行首）

### 排版精度

拿 LibreOffice 的转换结果做比对（8 份真实的中文法律文书，共 73 页）：**8 份页数全部一致**，段内行距精确匹配，首行缩进、中西文间距、断行位置重合，全文逐字可回抽。文档内部的分页点仍有约 1% 的漂移（20 页的文档累计约 4 行），属于 LibreOffice 与 Word 之间本来就存在的差异范围。

关键在行网格。中文文档的 `w:sectPr` 里通常有 `<w:docGrid w:type="lines" w:linePitch="312"/>`，它规定单倍行高不是字体的自然行高，而要**向上吸附到 linePitch 的整数倍**，`w:line` 的倍数再乘在这之上。12pt 宋体自然行高约 17.2pt，在 15.6pt 的网格上要占满 2 格 = 31.2pt，再乘 1.3 倍行距 = 40.6pt。忽略这一步只会得到 22.6pt —— 整篇行密度高出近一倍，页数只有应有的六成。

还有一条不那么直观的规则：段落**最后一行**的倍数行距，额外部分是按**吸附前**的自然行高算的，不是吸附后的。少了这条区分，每个段落边界都会多出一点，段落密集的文档累积下来会平白多一整页。

**不渲染（但会留痕）**

- 表格框线 —— **单元格里的文字会以纯文本形式保留下来**
- 图片、文本框、艺术字
- 分栏、页眉页脚、脚注尾注
- 域（页码、目录、交叉引用）
- 多级编号列表的编号本身

遇到这些内容时，程序会**照常输出 PDF，并在界面上逐条列出哪里没能完整还原**，不会悄悄丢掉。

**其他已知近似**

- 制表符按一个全角空格宽度处理，没有实现真正的制表位
- 字符样式的开关型属性（粗体等）采用「后者覆盖」而非 OOXML 规定的异或语义
- 中西文自动间距取 0.2 em（对着 LibreOffice 实测标定）
- 不支持老式 `.doc` 二进制格式和加密文档，会明确提示先另存为 `.docx`
- 系统里没有 `宋体` / `黑体` 时会替换成 Noto Serif / Sans CJK，字形与行高会有细微差别；替换会在转换报告里列出

## PDF 压缩能压多少

**这四个档位压缩的是 PDF 里的图像。** 扫描件、照片型 PDF 收益明显；而以文字和矢量为主的 PDF（Word / LaTeX 导出的那种）只能省下对象流与交叉引用流的结构开销，通常很有限。界面会如实显示压缩前后的体积和百分比，也会在识别出「这份 PDF 基本没有图像」时明说。

护栏（都是硬性的）：

- **逐张比对**：重新编码后不比原来小，就保留原图
- **代际损失保护**：已经是 JPEG、又不需要降采样时，绝不重新量化一遍（那样只会又大又糊）
- **整体兜底**：输出不比输入小就原样返回原文件
- **从不放大**，只在超过 DPI 上限时降采样
- 加密 PDF、带数字签名的 PDF 一律拒绝处理并说明原因
- 转灰度是**独立的、默认关闭的**选项 —— 那是内容改变而不是压缩，扫描件上的红色公章和签名笔迹一转就没了

## 已知不支持

- **HEIC / HEIF（iPhone 直出照片）**。解码需要系统的 libheif C 库，与绿色单文件分发的目标冲突。请先在系统相册里导出为 JPEG 或 PNG。

## 字体

界面字体优先使用系统自带的中文字体（macOS 上是 PingFang SC，Windows 上是微软雅黑，Linux 上是 Noto Sans CJK）。

导出 PDF 时会把用到的**字形子集内嵌进文件**，这样在没装对应字体的机器上打开也不会变成方框，并且文字可以选中、搜索、复制。内嵌时会读取字体的 `fsType` 标志，字体作者禁止内嵌的一律跳过并换用其他字体。

如果系统里一个中文字体都没有（常见于精简的 Linux 容器），程序会在启动时给出提示。安装 `fonts-noto-cjk` 或思源黑体即可。

## 从源码构建

需要 Rust 1.85 或更高版本。

```bash
git clone https://github.com/zzhtl/pdftools.git
cd pdftools
cargo run --release -p pdftools
```

Linux 上需要先装构建依赖：

```bash
sudo apt-get install -y libxkbcommon-dev libwayland-dev libx11-dev \
  libxcursor-dev libxrandr-dev libxi-dev libgl1-mesa-dev libegl1-mesa-dev \
  libxcb-render0-dev libxcb-shape0-dev libxcb-xfixes0-dev
```

### 工程结构

```
crates/pdfcore/   核心逻辑，不依赖任何 GUI，因此能在无显示器的环境里跑全部测试
crates/pdftools/  egui 界面壳
```

```bash
cargo test --workspace     # 全部测试，不需要显示器
cargo clippy --workspace --all-targets
```
