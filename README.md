# pdftools

跨平台桌面 PDF 工具箱。单文件绿色程序，**不联网、不上传、文件不出本机**。

用 Rust + egui 写成，Windows / macOS / Linux 三平台都有预编译包。

## 功能

| 功能 | 说明 |
| --- | --- |
| **多图片转 PDF** | 拖进来、拖动排序、一键合成。页面尺寸与比例逐张跟随图片，没有白边 |
| **Word 转 PDF** | 纯 Rust 自研排版，不需要装 Word 或 LibreOffice。保真度有明确边界，见下文 |
| **PDF 压缩** | 四个档位。针对 PDF 内的图像重新编码，带多重护栏，绝不会越压越大 |
| **图片批量压缩** | 输出到指定目录，不改动原文件 |

### macOS 首次打开会被拦截

本项目**没有 Apple 开发者签名**，所以 macOS 会提示「无法打开，因为无法验证开发者」。这不是程序有问题，处理方式二选一：

- 在 Finder 里**右键点击** `pdftools.app` → **打开**，在弹窗里再点一次「打开」；或者
- 终端执行：`xattr -dr com.apple.quarantine /path/to/pdftools.app`

### Windows SmartScreen

同理，未签名程序首次运行会被 SmartScreen 拦。点「更多信息」→「仍要运行」。

## 关于「不失真」

图片转 PDF 时，程序按下面的顺序逐张决定怎么处理，并在完成后如实报告每张图走了哪条路径：

1. **原图直通（零损失）** —— 源文件已经是 JPEG、不需要旋转、也不超过 DPI 上限时，**原始字节整段搬进 PDF**，不解码也不重新编码。这是真正意义上的零损失，有一条集成测试直接断言「PDF 里的流字节 == 源文件字节」。
2. **无损** —— 以原始像素配合 Flate 存储，像素完全一致。
3. **重新编码** —— 只有需要旋转（EXIF 方向）或超过 DPI 上限时才发生。

第 2 和第 3 条之间怎么选，**不靠猜图片是不是照片，而是两种编码各估一次体积后按实测结果决定**。截图和线稿的无损体积远小于 JPEG，会自然选到无损，从而避开 JPEG 在文字边缘产生的振铃（那正是俗称的「发虚」）；照片的无损体积是 JPEG 的十几倍，会自然选到 JPEG。

还有一条兜底：如果降采样加重新编码之后**反而比原文件更大**，就退回原图直通。这种情况在源文件本就是高压缩率 JPEG 时会出现，此时「压缩」既不省空间又白白损失一代画质。

「高质量」档的 DPI 上限是 300 —— 印刷级精度，肉眼看不出差别。低于上限的图片一个像素都不会动。

## Word 转 PDF 的支持范围

这一项是**纯 Rust 自己实现的排版引擎**，不调用任何外部程序。好处是绿色单文件、离线可用；代价是保真度有边界。请务必先看清楚：

**支持**

- 段落、粗体 / 斜体 / 下划线 / 删除线、字号、字体颜色
- 对齐（左 / 居中 / 右 / 两端对齐）
- 缩进（含「首行缩进 2 字符」这类以字符为单位的写法）
- 段前段后间距、行距（倍数 / 固定值 / 最小值）
- 页面尺寸与页边距、显式分页符
- 中西文混排，按字符自动选用中文字体或西文字体
- 符合 UAX #14 的断行，含中文标点避头尾（句号、逗号不会跑到行首）

**不渲染（但会留痕）**

- 表格框线 —— **单元格里的文字会以纯文本形式保留下来**
- 图片、文本框、艺术字
- 分栏、页眉页脚、脚注尾注
- 域（页码、目录、交叉引用）
- 多级编号列表的编号本身

遇到这些内容时，程序会**照常输出 PDF，并在界面上逐条列出哪里没能完整还原**，不会悄悄丢掉。

**其他已知近似**

- 制表符按一个全角空格宽度处理，没有实现真正的制表位
- 字符样式的开关型属性（粗体等）采用「后者覆盖」而非 OOXML 规定的异或语义
- 不支持老式 `.doc` 二进制格式和加密文档，会明确提示先另存为 `.docx`

## PDF 压缩能压多少

**这四个档位压缩的是 PDF 里的图像。** 扫描件、照片型 PDF 收益明显；而以文字和矢量为主的 PDF（Word / LaTeX 导出的那种）只能省下对象流与交叉引用流的结构开销，通常很有限。界面会如实显示压缩前后的体积和百分比，也会在识别出「这份 PDF 基本没有图像」时明说。

护栏（都是硬性的）：

- **逐张比对**：重新编码后不比原来小，就保留原图
- **代际损失保护**：已经是 JPEG、又不需要降采样时，绝不重新量化一遍（那样只会又大又糊）
- **整体兜底**：输出不比输入小就原样返回原文件
- **从不放大**，只在超过 DPI 上限时降采样
- 加密 PDF、带数字签名的 PDF 一律拒绝处理并说明原因
- 转灰度是**独立的、默认关闭的**选项 —— 那是内容改变而不是压缩，扫描件上的红色公章和签名笔迹一转就没了

## 已知不支持

- **HEIC / HEIF（iPhone 直出照片）**。解码需要系统的 libheif C 库，与绿色单文件分发的目标冲突。请先在系统相册里导出为 JPEG 或 PNG。

## 字体

界面字体优先使用系统自带的中文字体（macOS 上是 PingFang SC，Windows 上是微软雅黑，Linux 上是 Noto Sans CJK）。

导出 PDF 时会把用到的**字形子集内嵌进文件**，这样在没装对应字体的机器上打开也不会变成方框，并且文字可以选中、搜索、复制。内嵌时会读取字体的 `fsType` 标志，字体作者禁止内嵌的一律跳过并换用其他字体。

如果系统里一个中文字体都没有（常见于精简的 Linux 容器），程序会在启动时给出提示。安装 `fonts-noto-cjk` 或思源黑体即可。

## 从源码构建

需要 Rust 1.85 或更高版本。

```bash
git clone https://github.com/zzhtl/pdftools.git
cd pdftools
cargo run --release -p pdftools
```

Linux 上需要先装构建依赖：

```bash
sudo apt-get install -y libxkbcommon-dev libwayland-dev libx11-dev \
  libxcursor-dev libxrandr-dev libxi-dev libgl1-mesa-dev libegl1-mesa-dev \
  libxcb-render0-dev libxcb-shape0-dev libxcb-xfixes0-dev
```

### 工程结构

```
crates/pdfcore/   核心逻辑，不依赖任何 GUI，因此能在无显示器的环境里跑全部测试
crates/pdftools/  egui 界面壳
```

```bash
cargo test --workspace     # 全部测试，不需要显示器
cargo clippy --workspace --all-targets
```
